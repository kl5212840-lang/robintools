# /review — 审查内容改动

## 触发

用户输入 `/review` 或 `/review <搜索词>`。

- `/review` — 审查 `git diff --staged` 中的所有改动
- `/review <搜索词>` — 先搜索匹配文件，再审查该文件的改动（staged 或 working tree）
- `/review --deep` — 深度审查，额外执行联网验证

## 执行步骤

### 第 1 步：确定审查范围

**无参数**：运行 `git diff --staged` 获取所有已 stage 的改动。

**有参数**：按 `/edit` 命令的搜索逻辑找到目标文件，然后检查：
- `git diff --staged -- <path>`（已 stage 的改动）
- 如果 stage 无改动，则 `git diff -- <path>`（working tree 改动）
- 如果都无改动，报告"无改动"并退出。

如果搜索返回多条结果，让用户选择。

### 第 2 步：提取变更内容

从 diff 输出中提取：
- 新增的行（`+` 开头）
- 删除的行（`-` 开头）
- 变更的文件列表

只分析 diff 中出现的行及其上下文（前后 3 行），不读取整个文件，除非上下文不足以判断。

### 第 3 步：逐项检查

对每条变更执行以下检查。每个检查项标注：文件、行号、严重程度、具体问题。

#### 3.1 错别字与格式

- 中文错别字（的/地/得、在/再、做/作 等常见混淆）
- 中英混排空格（中文与英文/数字之间应有空格："安装 Node.js" 不是 "安装Node.js"）
- 标点符号（中文内容应用中文标点：。——，而非英文标点）
- 专业术语拼写（CLI 不能写成 cil、API 不能写成 api、VS Code 不能写成 vscode）
- 重复文字、漏字

#### 3.2 事实错误

- **版本号**：搜索新增内容中的版本号（如 `v2.1.15`），是否与常识一致或在近期官方公告中出现过明显变化
- **命令语法**：`CodeBlock` 中的命令是否语法正确（bash/powershell 命令是否有明显语法错误）
- **平台归属**：命令是否放在了正确的平台条件分支下（如在 `isWin` 分支下出现了 `brew` 命令）
- **文件路径**：如果提到具体文件路径，是否在对应平台下正确（Windows 用反斜杠、Unix 用正斜杠）
- **API 参数名**：配置字段名是否与工具官方文档一致（如 `base_url` vs `baseUrl`、`api_key` vs `apiKey`）

**判断标准**：确凿错误标记为 ❌，疑似问题标记为 ⚠️。不确定的不判。

#### 3.3 死链检查

从 diff 的 `+` 行中提取所有 URL：
- `https://...`、`http://...`
- 如果 URL 在 `Callout` 或普通文本中，也在 `<a href="...">` 中

对每个 URL 使用 WebFetch 检查可访问性（只做 HEAD 请求，不下载全文）。

**注意**：链接检查仅限新增的 URL（`+` 行中的）。已存在的 URL 不在本次审查范围内。

#### 3.4 标签检查

如果改动了 `articles/index.ts` 中的 `tags` 数组，或指南 `registry.ts` 中的 `searchText`：

- 标签是否与已有标签体系一致（检查同文件中的其他标签用法）
- 同一概念是否用了多种写法（如已有 `claude-code` 标签，新增的是否写了 `ClaudeCode`）
- 标签是否冗余（同一文章的标签中有无明显同义词重复）

`<搜索词>` 模式下载入完整的 `index.ts` 或 `registry.ts` 做跨条目比较，否则只检查 diff 本身。

#### 3.5 SEO 检查

- **标题**：如果是新文章，`title` 是否 ≤ 60 字符（中文约 30 字），是否包含核心关键词
- **摘要**：`summary` 是否 ≤ 160 字符（中文约 80 字），是否独立成段可读懂
- **标题层级**：`<h2>` / `<h3>` 是否按序使用（不跳级，如 h2 后不能直接 h4）
- **图片 alt**：如果新增了 `<img>` 或 `<Image>` 标签，是否有 `alt` 属性
- **meta 覆盖**：新文章路由是否已在对应的 `page.tsx` 中有 `generateMetadata`

#### 3.6 措辞风格

对 diff 的 `+` 行做词法匹配，检测以下反模式。只标 ⚠️（建议），不标 ❌（不阻断发布）。

| 反模式 | 触发词/句式 | 说明 |
|--------|------------|------|
| 拟人化 | 说谎、欺骗、杀掉(进程)、杀死(进程)、知道、试图、想、认为 | 工具和人称主语不搭配。kill 建议用"终止"替代 |
| 绝对断言 | 终极、最终真相、唯一真相、100%、绝不会、永远不会、绝对不 | 技术写作不应要求读者信任作者而非证据 |
| 自我指涉 | "这条(列在/写在)这里(是为/用来)"、"我想(说/表达)"、"这里要(说明/解释)" | 直接陈述内容，不解释为什么要写这段 |
| 冗余修饰 | "30 秒"、"一句话"、"只需三步"、"超简单"、"一键搞定"、"轻松" | 去掉数字承诺和程度副词，让用户自己判断 |
| 口语称呼 | 你怎么知道、你知道吗、说白了、其实、讲真、(标题/小标题用"核心认知") | 技术文章用"如何/怎么"替代"你如何/你怎么" |
| 戏剧化 | 爆炸、魔法、神奇、令人震惊、不可思议、颠覆 | 非技术术语的夸张表达 |

**豁免白名单**（不匹配时不会误报）：
- `幽灵缓存` — GitHub #1254 的社区术语，已确立
- `杀死僵尸进程` — 操作系统领域术语，非拟人
- `杀掉` → 如出现在代码块（`CodeBlock`）内，豁免

**输出格式**：`⚠️ 措辞 — <反模式>：建议 "<触发文本>" → 改为平实表达`

#### 3.7 本地环境泄露

对 diff 的 `+` 行做以下检查。**全部标 ❌（阻断发布）**。

| 泄露类型 | 触发模式 | 说明 |
|---------|---------|------|
| 真实项目路径 | `E:`、`C:\\Users`、`/home/` 等真实磁盘路径前缀 | 示例/配置中应使用 `<project-path>` 或 `~/your-project` 等占位符 |
| 本地用户名 | Windows 用户目录格式（`C:\Users\<name>`）、Unix home 格式（`/home/<name>`）的**非占位符**写法 | 检查 `<your-user>`、`你的用户名` 是否被误写为 `ukl` 等真实值 |
| 本地 IP 地址 | `192.168.x.x`、`10.x.x.x`、`172.16-31.x.x` | 示例中应使用 `127.0.0.1` 或 `localhost` |
| 真实 API Key / Token | Arnold 格式（`ark-`）、DeepSeek 格式（`sk-`）、GitHub 格式（`ghp_`）出现在 diff 中 | pre-push hook 已在第 3 层扫描，此处做内容提前拦截 |

**豁免**：
- `127.0.0.1` / `localhost` — 本地回环地址
- 占位符写法：`C:\Users\你的用户名\`、`/home/your-user/`、`<project-path>`、`/path/to/your-project`
- `~/` 开头（Unix/Mac 标准写法）→ 不会被解析为真实路径
- 代码块（`CodeBlock`）内的 `E:` 驱动器字母 → 仅适用于 Windows 命令/路径示例

**设计原因**：文章是公开的，任何人打开都能看到。里面出现本机真实路径 = 泄露了作者的操作环境和潜在的文件结构信息。所有示例必须用占位符。

**输出格式**：`❌ 本地环境泄露 — <类型>：建议将 "<真实值>" → "<占位符>"`

### 第 4 步：汇总评分

| 检查项 | 结果 |
|--------|------|
| 错别字与格式 | ✅ 0 问题 / ⚠️ N 建议 / ❌ N 问题 |
| 事实错误 | ✅ 0 问题 / ⚠️ N 疑似 / ❌ N 确凿 |
| 死链 | ✅ 全部可达 / ❌ N 个不可达 / ⊘ 无新增链接 |
| 标签 | ✅ 一致 / ⚠️ N 建议 / ⊘ 无标签改动 |
| SEO | ✅ 合规 / ⚠️ N 建议 / ⊘ 无 SEO 影响 |
| 措辞风格 | ✅ 0 问题 / ⚠️ N 建议 |
| 本地环境泄露 | ✅ 0 问题 / ❌ N 问题 |

### 第 5 步：输出结论 + 交互选择

**全部 ✅**：
```
✅ 审查通过 — 未发现问题。

   [1] 发布上线     → /publish
   [2] 继续编辑     → /edit <file>
   [3] 完成         → 结束

   输入数字：
```

**有 ⚠️ 建议（无 ❌）**：
```
⚠️ 审查通过（有 N 条建议）

<逐条列出建议，标注文件:行号>

   [1] 仍然发布          → /publish
   [2] 修复建议后重审     → /edit <file>
   [3] 深度审查一次       → /review <file> --deep
   [4] 完成               → 结束

   输入数字：
```

**有 ❌ 问题**：
```
❌ 审查未通过 — 发现 N 个需要修复的问题

<逐条列出问题，标注文件:行号、严重程度、修复方案>

   [1] 打开文件修复       → /edit <file>
   [2] 查看完整问题清单   → 重新列出所有问题
   [3] 完成               → 结束（问题未修复，后续 /publish 会再次拦截）

   输入数字：
```

**用户只需输入一个数字**，Claude 自动执行对应操作。

## 深度审查（--deep）

当用户指定 `/review --deep` 时，在标准检查之外追加：

1. **官方文档交叉验证**：对涉及配置字段、API 参数、价格、版本号的变更，WebFetch 对应工具的官方文档页面对比核实
2. **国内网络可达性**：对 `Callout` 中提到的域名，标注国内直连情况（已知的被墙域名可直接判定，不确定的标注"需人工验证"）

深度审查耗时长（需多次 WebFetch），仅在有重大内容变更时使用。

## 约束

- 操作等级：L1（diff 读取），仅为内容审查，不执行任何写入
- `--deep` 模式额外使用 L2（WebFetch 联网验证）
- 只分析 diff 内容，不审查整个文件
- 不自动修改任何文件
